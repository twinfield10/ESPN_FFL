The width is real, not rot

A board is up to 1,699 columns because five sources each carry a full stat line — BOL 282, FP 281, PINNY 281, ATH 281, ESPN 144, plus USG 138, MEAN 138 and TRUE 56. Narrowing the store means deciding a source's stat line does not need to be queryable after the blend — a modelling decision, not a cleanup.

05 — The button

What "Refresh This League" actually refreshes

It shells out to one command, with no --what:

python -m Scripts.refresh --league <display_name> --season 2026
# no --what, so DEFAULT_WHAT = ("lineups",)

That is the lineups artifact and nothing else. Concretely, pressing it:

Does it refresh…AnswerDetail
Current lineups / startersyes Re-fetches every matchup's box score from ESPN, so who is in which slot is current.
Rosters and waiver addsyes Same call. A player added an hour ago appears.
Live and final scoresyes points comes straight off the box score.
Free-agent poolyes build_fa_market re-samples the wire, stamped with the current week.
The blended projectionrecomputed Re-blends from the source files already on disk — for every week from 1 to now, not just this one.
The projection sourcesno No scraping. FantasyPros, the books and The Athletic are whatever the 06:00 job left.
The draft boardno --what board is nightly-only.
Matchups / standingsno --what team_stats is nightly-only. This is why the Matchup tab used to lag on a Tuesday.
Injuries, depth charts, NFL datano All R-side, nightly.

Cost: ~8.5s per league measured in the 2026-09-16 nightly (85s for ten). It grows with the season — the build loops weeks 1..current — toward roughly 23s by week 18.

Under the default configuration, the button changes nothing the user can see

app/store.DEFAULT_SOURCE is "s3". Scripts.refresh contains no reference to S3 and never pushes. So the button spends 8–23 seconds of ESPN round-trips, writes Data/Store/, and calls st.rerun() — and the rerun reads the bucket, whose fingerprint has not moved, and re-renders identical numbers. The in-code comment ("store_mtime changed, so the cached readers miss") is true only under ESPN_FFL_STORE_SOURCE=local.

Two fixes, and they point in opposite directions. If the button is for the operator on this laptop, have it push after a clean build. If it is for a deployed app, it should not exist in that form at all — a web viewer cannot be allowed to trigger nine ESPN round-trips from a render path.

fixed 2026-09-16 The first one. The button now runs Scripts.refresh --league X --push, publishing only the artifacts it built and skipping bytes S3 already holds, and greys out for five minutes after a successful run. The second is still open: a session-scoped cooldown is right for one operator on one laptop and is not a rate limit.

08 — Temporal guards

What already stops the clock, and what doesn't

The repo has more kickoff-awareness than it looks like from the outside. It is just wired into the display layer rather than the ingest layer.

The FantasyPros freeze is wrong in both directions at once

keep="first" freezes a whole week at its first capture, which in practice is the Tuesday or Wednesday 06:00 run. So Thursday's opener is protected — and so is Sunday's 1 pm slate, four days before it kicks off. Every injury designation, every Friday practice report, every Saturday inactive between that first capture and kickoff is discarded. Week 2's FantasyPros numbers were captured 2026-09-16 and will not move again, whatever happens between now and Sunday.

That is the argument for making the guard per-game rather than per-week: both failures are the same missing distinction.

Be honest about the magnitude: today it is small, and that is luck

The largest single move on an already-played game was Jalen McMillan's week-1 TRUE_Points going 8.05 → 6.37 after he had finished the game on 0.0. Most rows moved by hundredths. The reason it is not worse is that no NFL game kicks off before 06:00, so the nightly's one daily write always lands pre-kickoff for that day's games, and books retire a market once its game starts, so there is usually nothing new to overwrite with.

None of that is enforced anywhere. It holds because of the cron slot and because of how sportsbooks behave. Move the nightly to 18:00, add a second daily run, or press the sidebar button at 4 pm on a Sunday, and every number in the table above gets larger with no warning and no log line. The guard is worth building while the cost of not having it is still two decimal places.

And one column the live loop does rewrite, 144 times a day

Scripts.live.PATCH_COLUMNS includes projPoints — ESPN's own weekly projection, which moves continuously during a game. Every ten minutes through a slate, the live job overwrites it with ESPN's in-game number. The ESPN_-prefixed columns are correctly left alone, so between one nightly and the next, espn_unpriced = projPoints − ESPN_Points drifts from a real audit residual into the gap between a live projection and a pre-game one. It is the one place the live job's "touches no projection column" contract does not hold, and it holds for every column that carries a source prefix — which is why it was easy to miss.

10 — Proposal

Freeze a projection at its own kickoff

The rule, stated once: a projection column for player P in week W is writable while P's team's week-W game is pre, and immutable from the moment it is anything else. Not per week, not per slate — per game, because that is the grain at which the fact "this is now history" becomes true.

Everything needed to enforce it already exists. Scripts.game_state.states(season, week) returns one row per NFL team per week with state, game_elapsed, game_locked and the kickoff time, cached for 300 seconds and refreshed on demand. It is read at blend step 6b to compute LIVE_Points. The proposal is to read it one step earlier and let it gate the write, not just the display.

The worked example

NE @ SEA, Wednesday 20:20

At Thursday 06:00 the nightly runs. game_state.states(2026, 1) reports NE=post, SEA=post, and pre for the other 30 teams.

  • Every NE and SEA player's *_Points and *_<stat> cells for week 1 are carried forward byte-for-byte from the stored frame.
  • Their points, ACT_* and LIVE_* are written normally — the game is final and the actual is the answer.
  • Every other team's week-1 projection rebuilds exactly as it does today, with Thursday's injury news in it.
  • On Sunday at 06:00, the 26 teams playing at 13:00 are still pre, so Saturday's inactives reach them. The two Thursday teams stay frozen.

Same command, same cadence, same cost. The only thing that changes is that a cell whose game has started is copied rather than recomputed.

Implementation order

steps 1–4 built 2026-09-16 Scripts/kickoff_freeze.py, applied at the store boundary in Scripts.refresh, with Scripts.scrape_FP moved from a per-week freeze to a per-game one. Step 5 rides on the button decision in §05.

  1. Stamp, before gating. Add projection_frozen_at to the lineups frame, written at the moment a row first goes pre → not-pre. A week of that data alone says how much movement the gate would have prevented, per source, and it costs one column.
  2. Gate the blend. In clean_lineups, after the existing gs.board(...) call at step 6b, carry forward the projection columns for any (week, player) whose team is not pre. The frame and the board are already both in hand at that point — this is a merge, not a new fetch.
  3. Drop projPoints from PATCH_COLUMNS for locked rows, so the live loop stops moving it mid-game.
  4. Gate the source scrapes — generalise 4Casters' if not g["live"] into the shared helper and apply it to BOL, Pinnacle and The Athletic. Replace FantasyPros' per-week keep="first" with the same per-game rule.
  5. Gate the button. Whatever is decided in section 05, the manual path must go through the same freeze — it is the only writer with no timing protection at all.

Steps 1–3 are small, sit inside code paths that already have the game-state board loaded, and close the whole in-store exposure. Step 4 is the larger one and can wait; it closes the source files, which are currently protected by market behaviour rather than by us.

The one thing to check before building any of it

This report establishes that projection columns for played games do change. It does not establish that they change wrongly in every case — some of the movement in the 09-11 → 09-14 window is legitimate pre-kickoff line movement on Sunday morning, captured before 13:00. Step 1's stamp is what separates the two, and it is deliberately first for that reason. Build the measurement before the guard; the plans directory is full of cases where the opposite order shipped a fix for the wrong thing.
